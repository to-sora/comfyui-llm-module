## 1. 架構總覽

```
                         ┌──────────────── ComfyUI 行程 (HTTPS :8188, 0.0.0.0) ─────────────────┐
OpenAI client ──POST──▶  │ plugin gateway (/v1/chat/completions)                                │
                         │   │ 把 messages JSON 字串化塞進 prompt graph                          │
                         │   └─HTTPS 回打自己 /prompt ─▶ ComfyUI 佇列 ─▶ LLMModel → LLMChat 節點 │
                         │        ▲  websocket (/ws) 收 llm.token / executing 事件               │
                         │        └─ GET /history/{id} 取結果 → POST /history 刪除               │

                         │          prefix snapshot(CPU) / Qwen 視覺 FP32 局部預填               │

                         └──────────────────────────────────────────────────────────────────────┘
```

## 2. 好處

1. **單一 VRAM 擁有者**：LLM 透過自製 `LLMPatcher`（`plugin/src/main/patcher.py`）登記進 ComfyUI
   `model_management`，SDXL 與 LLM 由同一套機制決定共存、卸載到 RAM、恢復。
   用 llama.cpp 在同一行程時，ComfyUI 看不到 llama.cpp 自己配置的 CUDA 記憶體，這點是本 repo 真正的長處。
2. **卸載到 RAM 不重讀磁碟**：完整 detach 時權重（含 bnb quant_state）搬到 CPU，恢復時不重新量化
   （todo 記錄 27B FP4 17.9 GB offload/restore、磁碟載入維持一次）。
3. **匯入流程 fail-closed**：`convert.py` 不覆寫既有目標、staging + rename；`assemble.py` 嚴格比對 key/shape；
   用 llama.cpp 當參考做 tokenizer／template／logits(KL)／greedy／vision 一致性關卡。方法論正確。
4. **前綴快照支援混合（Gated DeltaNet 遞迴狀態）模型**：`prefix_cache.py` 對 linear-attention 層對齊 64 token
   並保存遞迴狀態，這比單純 KV 前綴困難。
5. **取消與清理完整**：每個 token 檢查 `throw_exception_if_processing_interrupted`；逾時、斷線會取消原生 prompt、
   等執行停止後刪 history（`gateway_jobs.py`、`gateway_cleanup.py`）。
6. **Studio 資料耐久性**：SQLite WAL、ULID、SSE `Last-Event-ID` 續傳、重啟後把卡住的 run 標成 interrupted、
   圖片血緣（parents）、SHA256、本機原圖、遮罩外像素精確保留（`image_finish.py` composite）。
7. **基本安全意識**：`trust_remote_code=False`、safetensors、圖片 URL 只允許 data URL 或本機 loopback（防 SSRF）、
   16 MB 圖片上限、`Image.MAX_IMAGE_PIXELS`。
8. **文件誠實**：失敗案例（9B FP4 工具錯誤、窄遮罩紅星失敗、可選工具指引 11/54 失敗）都有記錄。
9. **依賴版本全部釘死**，快取路徑都收在專案目錄內。

## 3. 壞處（宏觀）

1. **請求路徑太長**：OpenAI 請求 → JSON 字串化進 graph → TLS 回打自己 `/prompt` → 佇列 → 節點 →
   TextStreamer → `send_sync` websocket → gateway → SSE → Studio → SQLite → Studio SSE → 瀏覽器。
   每次請求至少 4–5 次 loopback TLS 往返；base64 圖片會在 graph、queue、history 中被複製多次。
2. **服務引擎效能**：transformers + bitsandbytes 一次只服務一個請求（`n=1`、ComfyUI 單佇列），
   沒有連續批次；混合層預設跑 PyTorch reference kernel（§6 B-P3）。比 llama.cpp 慢很多（§5）。
3. **GGUF 路徑有損且吃磁碟**：Q4_K_M/Q6_K → FP16（2 bytes/param）→ 執行時再量化成 NF4 → 再寫 NF4 快取。
   雙重量化誤差，磁碟用量約為原 GGUF 的 4–5 倍（§4、§5）。
4. **預設對 LAN 開放**：兩個服務綁 `0.0.0.0`、無登入。使用者決定只在可信任 LAN 內使用，本文件不處理。
5. **Studio 寫入放大**：每個串流 token 一次 SQLite transaction（重寫整則訊息 + 插入 event + fsync），
   每個 token 還會把整份 run trace JSON 解析一次（§4.3、§6 B-I1/I2）。所有 SQLite、PNG 編碼、ZIP 都在事件迴圈上同步執行。
6. **無限成長的資料**：events 表、ComfyUI input/output 目錄、run trace 都沒有清理（§6 B-I6）。
7. **不可攜／不可重現**：`models.yaml`、`imports.yaml` 寫死 `/mnt/DATA9/...`；測試需要真 GPU、本機模型與
   `~/UAT-firefox`；證據不在 git。沒有可在 CI 執行的單元測試。
8. **全域副作用**：plugin 在 ComfyUI 行程內 monkeypatch `socket.getaddrinfo`（強制 IPv4）、改寫 `TMPDIR`、
   `HF_HOME`、`XDG_CACHE_HOME` 等，影響所有其他節點（`ipv4.py`、`settings.py:13-26`）。
9. **重複程式碼**：`network.py`、`processes.py`、`tls.py`、`pip_ipv4.py` 在 plugin 與 server 各一份，容易漂移；
   還留有已移除 GGUF 後端的殘骸（`discovery.py:34` 的 `q8_0/q4_0`、`registry.py:38-39`）。

## 4. 對電腦的負擔（讀寫次數與頻率）

標示「估算」的數字是依程式碼推導的數量級，請實作者用 §7 T-0.3 的量測工具確認。

### 4.1 磁碟容量（以 27B / 9B 為例，估算）

| 項目 | 27B（Q4_K_M 來源） | 9B（Q6_K 來源） | 依據 |
|---|---|---|---|
| 原始 GGUF（保留） | ≈ 16.5 GB（≈4.85 bpw） | ≈ 7.4 GB（≈6.56 bpw） | imports.yaml |
| 匯入 FP16 safetensors | ≈ 54 GB（27e9×2B） | ≈ 18 GB | `convert.py:15,39` 預設 float16 |
| NF4 磁碟快取 | ≈ 15–17 GB | ≈ 5–6 GB | `weight_cache.py`，`estimate.py:36` 的 0.516 B/param |
| 合計 | **≈ 86–88 GB** | **≈ 30 GB** | llama.cpp 只需 GGUF + mmproj |

另外：models.yaml 同時有 `Qwen3.8-27B-OBLITERATED`（原始 HF 權重）與 `Qwen3.8-27B`（從同一個 OBLITERATED
模型的 Q4_K_M 解量化），兩者各自產生一份 NF4 快取。匯入版是同一模型的有損副本（`plugin/doc/formats.md` 已承認）。
使用者決定 Qwen3.8-27B 必須保留；Path B（§5.3）可以直接用原 GGUF 服務它，省下 FP16 中間檔與 NF4 快取約 70 GB。

### 4.2 GPU / RAM / PCIe

- **冷啟動第一次**：讀 FP16（27B ≈ 54 GB）→ GPU 上量化 → **在第一個請求內同步寫出** NF4 快取（≈ 15–17 GB）
  （`hf_load.py:47` → `weight_cache.save`）。之後每次冷啟動讀 NF4 快取 ≈ 15–17 GB。
- **LLM ↔ SDXL 互換**：`runtime.py:44` 每次 LLM 呼叫都 `load_models_gpu(memory_required=…)`。
  27B NF4 在 24 GB 卡（`install-gguf.sh` 的 sm_89）上無法與 SDXL 同駐，Studio 每一輪
  「LLM → SDXL → LLM 檢查」至少 2 次 17.9 GB 搬移（≈ 36 GB PCIe）。9B 可共存（`ram_accept.py` 斷言 Both models fit）。
- **CPU 端複本不是 pinned memory**（`hf_move.py:20-21` 用一般 `.to()`），H2D 恢復速度約只有 pinned 的一半（估算）。
- **兩份前綴快照**留在 CPU，每次命中都整份複製回 GPU（`prefix_state.py:51` `clone(snapshot, device)`）。
- **HQQ KV**：transformers 的 `QuantizedLayer` 每個 decode step 解量化整段快取，每 32 token 重量化整段；
  本 repo 的 `QuantizedSlidingLayer.update`（`kv_cache.py:13-24`）**每個 token** 解量化＋重量化整個 window。
  省的是靜態記憶體，代價是每 token O(context) 的額外運算（§5）。

### 4.3 Studio SQLite 寫入頻率（最嚴重的 I/O 熱點）

一則串流回覆有 N 個 SSE 封包、最終文字 S bytes 時：

| 動作 | 次數 | 每次成本 | 位置 |
|---|---|---|---|
| `delta()`：`BEGIN IMMEDIATE` → 讀 assistant message 並 JSON 解析 → 附加文字 → **重寫整個 parts_json** → `update()` 再讀一次並解析 → INSERT events → COMMIT | N | O(S) 寫入 + 1 次 fsync（WAL + 預設 synchronous=FULL） | `message_parts.py:4-17`、`store.py:60-63` |
| `e.check(run)`：`SELECT * FROM runs` 並 **json.loads 整份 trace_json** | N | O(trace 大小) CPU | `llm.py:28-29`、`engine.py:63-65` |
| `trace()`：讀整份 trace → append → 重寫整份 → 再讀一次 | 每輪 4–6 次 | O(trace) | `engine.py:57-61` |
| 圖片進度 event | 步數 × 張數（28 × 最多 8） | 1 INSERT + fsync | `image_events.py:11-14` |
| queue 通知 | 每次狀態變化 × 佇列列數 | INSERT | `run_worker.py:17-21` |

- 中文回覆特別糟：transformers `TextStreamer` 遇到 CJK 字元就逐 token flush，所以 N ≈ token 數。
- 估算：1,000 token 中文回覆 ≈ 1,000 次 commit/fsync、訊息重寫總量 ≈ S·N/2 ≈ 2 MB、WAL 寫入 ≈ 10–20 MB。
  若 `server/data` 在 HDD（文件說可為 symlink），1,000 次 fsync × 約 10 ms ≈ 10 s 的事件迴圈阻塞。
- trace 內含每一輪完整的 request body（整段對話）與每輪的 `/llm/status` 快照（`llm.py:23,44-45`），
  12 輪後可達數百 KB 到 MB 級；每個 token 解析一次 → 估算每則回覆 2–10 s 的事件迴圈 CPU。
- events 表永不清理：每個 token 一列、每個進度步一列，只在刪除對話時刪（`chat_store.py:37-38`）。

### 4.4 每次 Studio 回合的網路／檔案往返

- 每輪 `budget()` 會反覆呼叫 `/llm/token_count`（`context.py:11-19`），每次都重新套模板、
  **重新抓取並解碼每張圖**（經 `/view` loopback TLS）；接著真正的 LLM 呼叫再抓一次。
- 每輪 `attach()` 都把 512 px JPEG 再上傳到 ComfyUI input（`vision_messages.py:13`，覆寫但仍寫磁碟）。
- 每張生成圖：ComfyUI `SaveImage` 寫一份到 ComfyUI output → Studio `/view` 下載 → 再寫一份到 `data/assets`
  + WebP 縮圖（`workflows.py:16`、`image_finish.py:15-21`）。同一張圖存兩份；使用者決定保留 ComfyUI 那份，不清理。
- 每次編輯：來源 PNG、遮罩 PNG 以 prompt UUID 命名上傳到 ComfyUI input（`image_inputs.py:23,28`），同樣保留。
- `/api/uploads` 每讀一個 multipart chunk（aiohttp 預設 8 KiB）就重新讀一次並解析 `config.yaml`
  （`api_uploads.py:20`）→ 80 MB 上傳 ≈ 1 萬次 YAML 讀取。
- 小型但每請求都有的 YAML 讀取：gateway 讀 `config.yaml` 3 次、`catalog.styles()`/`recipe()` 每次呼叫都讀檔、
  `weight_cache.source()` 每次載入 glob 所有 `data/quantized/*/source.txt`。

## 5. 與 llama.cpp 的對比

本 repo 自己的參考步驟（`logit_reference.py`、`vision_reference.py`，llama-cpp-python 0.3.36、`n_gpu_layers=-1`、
`flash_attn=True`）已經證明：**llama.cpp 能在同一張 GPU 上直接跑這兩個 GGUF + mmproj**。

### 5.1 服務端能力

| 面向 | 本 repo（transformers 服務） | llama.cpp（llama-server / libllama） |
|---|---|---|
| 權重格式 | GGUF → FP16 HF → 執行時 bnb NF4 再量化 | 直接用 GGUF K-quant，mmap 載入，無轉換 |
| 品質 | 雙重量化（K-quant 誤差 + NF4 誤差）；9B 從 6.56 bpw 降到 ≈4.13 bpw | 原生 K-quant，可選 Q6_K/Q8_0 |
| 冷啟動 | 第一次讀 54 GB + 寫 15 GB；之後讀 NF4 快取 | mmap，page cache 命中時近乎即時 |
| KV 量化 | HQQ 4/8：每步解量化整段、定期重量化（可能累積誤差） | `-ctk/-ctv q8_0/q4_0/…` 以量化形式儲存，FA kernel 直接讀（量化 V 需 flash-attn） |
| 前綴重用 | 只有 system message，≤ 4096 token，混合模型對齊 64，最多 2 份 CPU 快照 | 每個 slot 自動重用整段 prompt 的最長共同前綴（`cache_prompt`）、`--cache-reuse` 位移重用、`--slot-save-path` 存到磁碟；新版本有 context checkpoint 支援 SWA/混合模型（請以目前版本確認） |
| 多輪對話 | 每輪重新 prefill 除 system 以外的整段歷史 | 前一輪的 KV 直接延用，只 prefill 新增部分 |
| 混合層 kernel | 預設 PyTorch reference（`kernel_policy.py` 每請求 unwrap）；FLA/causal-conv1d 試驗後退化，未啟用 | 原生 CUDA/CPU ggml op |
| 並行 | ComfyUI 單佇列、`n=1` | `--parallel N` slot + continuous batching |
| 工具呼叫 | 生成後 regex 解析，無約束解碼，失敗靠一次 repair 回合 | `--jinja` + `common/chat.cpp` 各模型家族 parser，可用 lazy grammar 約束 tool-call JSON |
| 推理內容 | `<think>` 被丟棄；Studio 永遠 `enable_thinking:false` | `--reasoning-format` 分離為 `reasoning_content`、處理 forced-open thinking、`--reasoning-budget` |
| 取樣 | temperature/top_p/top_k/min_p/seed | 完整 sampler chain：penalties、DRY、XTC、typical、mirostat、grammar、logit_bias |
| 視覺 | HF processor + transformers vision tower | libmtmd + mmproj（依版本有 image token 上下限參數） |
| API | chat completions 子集、無 logprobs、無 embeddings | chat/completions/embeddings/rerank、`/tokenize`、`/apply-template`、`/slots`、`/metrics` |
| 與 ComfyUI 記憶體整合 | **原生整合**（本 repo 的優勢） | 自己配置 CUDA 記憶體，ComfyUI 無法計量或卸載 |

結論：llama.cpp 在速度、品質、磁碟、前綴重用、工具約束上全面佔優；本 repo 唯一的結構性優勢是
「與 ComfyUI 共用一個 VRAM 管理者」。這個優勢可以用「llama.cpp 後端 + 會回報 VRAM、detach 時釋放 context 的
ModelPatcher 轉接層」保留下來（§5.3 Path B）。

### 5.2 GGUF 轉換格式逐項對比

本 repo 的匯入是 llama.cpp `convert_hf_to_gguf.py` 的**反方向**。文字權重交給 transformers
`integrations.gguf` 反轉；視覺投影器是手寫對照表（`importer/vision.py`）。

| 項目 | llama.cpp 匯出（HF → GGUF） | 本 repo 反轉（GGUF → HF） | 風險／建議 |
|---|---|---|---|
| 文字權重數值 | K-quant 量化 | gguf-py 精確解量化，再轉 **float16**（`convert.py:15,32`） | Qwen 系列以 BF16 訓練；建議預設 bfloat16，避免 FP16 範圍問題 |
| Qwen3-Next/3.5 線性注意力專屬轉換 | 依 `Qwen3NextModel.modify_tensors`：`A_log → -exp(A_log)`、`dt_bias` 改名、conv1d squeeze、`in_proj_qkvz` 重排、部分 norm 權重 +1（請對照當前版本原始碼） | 完全依賴 transformers 是否正確反轉 | 匯入後對每類張量加斷言；以長上下文 logit 測試驗證（§7 T-5.4） |
| 視覺 patch embed | Conv3d 沿時間維拆成 `v.patch_embd.weight` 與 `.weight.1` | `torch.stack(..., dim=2)`（`vision.py:32-33`） | 正確；需斷言 temporal_patch_size == 2 |
| 視覺 QKV | Qwen3-VL 保留融合 `attn_qkv`；Qwen2/2.5-VL 拆成 `attn_q/k/v`，且有 `ffn_gate` | 只認 `attn_qkv` 等 6 種 leaf（`vision.py:12-13`） | 其他 leaf 會丟出不友善的 `KeyError`（B-G2） |
| Qwen3-VL deepstack | 匯出 `v.deepstack.*` | 不在對照表 → `ValueError`（fail-closed，好） | 文件註明不支援 |
| mmproj metadata | `clip.vision.*`（patch size、merge size、image mean/std、projector_type、層數、hidden） | **完全忽略**，改用 `--base` 的 processor/config | base 不符時會靜默產生錯誤前處理（B-G3） |
| 文字 config | GGUF metadata（含 `rope.dimension_sections` M-RoPE） | `config.text_config = text_model.config`（`assemble.py:8`），由 transformers 從 GGUF 轉 | 斷言 rope_theta、mrope_section、layer_types、head_dim 等與 base 一致 |
| Tokenizer | `tokenizer.ggml.*`（tokens、merges、pre-tokenizer、special flags） | transformers 由 GGUF 重建 fast tokenizer，**取代** base tokenizer（`assemble.py:25-26`） | 只測 5 個字串、3 段對話（`token_parity.py:9-17`）；應全詞表比對（B-G5） |
| generation_config | 寫入 eos 等 metadata | 未從 base 複製 | 曾導致 EOS 問題，後以 tokenizer EOS 補救（B-G6） |
| 驗證對象 | — | logit parity 只驗 **FP16** 匯入；實際服務的是 **NF4** | 關卡驗的不是上線的東西（B-G4） |

建議：改成雙路徑，見 §5.3。另外，程式碼中 `kernels._gguf_kernel = False`（`convert.py:21`）顯示安裝的
transformers 有 GGUF kernel 路徑，值得評估能否在 transformers 內保留 GGUF 量化權重直接服務（未驗證，T-5.12）。

### 5.3 GGUF 雙路徑：設計與看法

看法：雙路徑可行，也值得做，但兩條路要有明確分工，而且 **Path B 應該用 llama.cpp 原生執行**，
不要用 transformers 在載入時解量化。

| | Path A：一次性轉成 HF repo 存磁碟 | Path B：執行時直接載入 GGUF |
|---|---|---|
| 做法 | `importer.convert`：GGUF → BF16 safetensors → 六道關卡 → 執行時 NF4/FP4 + NF4 快取 | 新 `GGUFEngine`（llama-cpp-python，repo 已釘 0.3.36，`install-gguf.sh` 已有），直接 mmap GGUF + mmproj |
| 權重精度 | 雙重量化（K-quant → NF4） | 原生 K-quant，沒有二次誤差 |
| 磁碟（27B） | GGUF ≈ 16.5 GB + BF16 ≈ 54 GB + NF4 快取 ≈ 15–17 GB | 只有 GGUF ≈ 16.5 GB + mmproj |
| 冷啟動 | 讀 NF4 快取 ≈ 15–17 GB | mmap；page cache 命中時幾乎不讀磁碟 |
| ComfyUI 記憶體整合 | 完整：卸載到 RAM、恢復不重讀 | 經 patcher 轉接：回報 VRAM、依 budget 選 `n_gpu_layers`、detach 時釋放（重載靠 page cache） |
| 與 SDXL 共存 | 只能整個換進換出 | 可把部分 layer 放 CPU（`n_gpu_layers`），27B 有機會與 SDXL 同駐、不必互換 |
| 多輪前綴重用 | 現有 system 前綴快照（HF 專屬） | llama.cpp 保留上一個 prompt 的 KV，自動重用最長共同前綴；混合模型能否部分回退需驗證（§8-7） |
| KV 量化 | HQQ（慢） | q8_0/q4_0 原生 |
| 速度 | 慢（bnb + reference kernel） | 快（原生 CUDA kernel） |
| 工具呼叫 | 現有 parser | 用 GGUF 內的 Jinja 模板組 prompt，輸出交給同一個 `tool_calls.parse`；可選 GBNF 約束 |
| 診斷／研究功能 | 完整（prefix probe、精度模式、kernel 模式） | 沒有（這些是 HF 專屬） |
| 適用情境 | 需要 HF 研究功能，或要和 HF processor 精確對齊時 | 日常服務的預設 |

為什麼不建議用 transformers 做 Path B（`from_pretrained(gguf_file=...)`）：它載入時一樣會解量化成完整 dtype，
再交給 bnb 量化，品質一樣是雙重量化；每次冷啟動都要做 CPU 解量化（27B 需要數十 GB RAM 和數分鐘，估算）；
唯一好處是磁碟不留 FP16。這等於「Path A 不存檔」，不值得另外維護。要省 FP16 磁碟，把 Path A 改成
「逐張量解量化 → 直接量化成 NF4 → 只寫 NF4 快取」即可（T-5.2）。

雙路徑的成本與控制方法：
- 兩個引擎行為容易分歧 → 定義共同 `Engine` 介面（`load(device, budget)`、`offload()`、`prepare()`、`chat()`、
  `cache_tensors()`、`diagnostics`），gateway、節點、Studio 不需要知道底下是哪一個。
- 回應格式要一致 → 兩條路徑都輸出 raw text，交給同一個 `model_response.parse`／`tool_calls.parse`。
- 測試加倍 → 寫「同一請求分別跑 A 與 B」的對照測試；llama.cpp 本來就是 parity 參考，B 等於讓參考上線。
- 舊的 `gguf_engine.py`（`2fb93c2`，在 `ebf4ca4` 移除）可以拿回來改。它每次請求都呼叫 `self.model.reset()`，
  會讓前綴重用完全失效，要拿掉；並改成自己組 Jinja prompt、加上 budget → `n_gpu_layers`。
- profile 用 `backend: gguf | transformers` 區分；同一模型可以有兩個 profile（`Qwen3.8-27B` 走 A、
  `Qwen3.8-27B-gguf` 走 B），方便對照。

Qwen3.8-27B 在兩條路徑的現況：
- A：`data/imported/Qwen3.8-27B` 已通過六關，NF4 與 FP4（含視覺前綴）已啟用。
- B：`logit_reference.py`、`vision_reference.py` 已用 llama-cpp-python 0.3.36 在同一張 GPU 上跑過這個 Q4_K_M
  + bf16 mmproj，代表技術上可行。
- VRAM（估算）：權重 ≈ 16.5 GB + mmproj ≈ 1 GB + q8_0 KV（16k context，只有 full-attention 層需要 KV）不到 1 GB
  + 工作空間，約 18–19 GB。單獨可放進 24 GB 卡；與 SDXL（≈ 7 GB）同時需要把部分 layer 放 CPU，或換進換出。

### 5.4 與 ComfyUI 記憶體管理的整合（現況與 Path B）

對照的是 upstream ComfyUI `872eb6a`（2026-10-18）；使用者本機的 `comfyui` 版本可能不同，請對照。

現況（transformers 路徑）是「ComfyUI 決定何時，plugin 自己決定怎麼搬」：

| 層級 | 誰決定 | 怎麼做 | 位置 |
|---|---|---|---|
| 載入到 GPU | ComfyUI `load_models_gpu` → `free_memory` 依它的排序先卸載別的模型 | plugin `partially_load` 自己載入或搬回（accelerate device_map） | `runtime.py:44`、`patcher.py:56-61` |
| 從 GPU 卸載 | ComfyUI `LoadedModel.model_unload` | `partially_unload` 回傳 0 → 一律 `detach` → plugin 用 `hf_move` 把整個模型搬到 CPU；沒有逐層 lowvram、沒有 pinned、不是 dynamic patcher | `patcher.py:63-68`、`hf_move.py` |
| CPU RAM 副本 | ComfyUI `RAMPressureCache`（upstream 預設快取模式） | 透過 `_comfy_cache_tensors` 量 CPU 大小（`caching.py:591-592`）；RAM 低於 headroom 時整個節點輸出被丟掉 → 弱引用 registry 失去 runtime → 權重釋放 → 下次從磁碟讀 NF4 快取 | `runtime.py:58-62` |

結論：是自動管理，但只有「全在 GPU／全在 RAM／整個丟掉」三種狀態。

Path B（llama.cpp）照同一個 patcher 契約實作：

| ComfyUI 呼叫 | Path B 做法 |
|---|---|
| `get_free_memory` | 不用改：CUDA 分支以 `torch.cuda.mem_get_info`（驅動層）加 torch 快取計算（`model_management.py:1811-1850`），看得到 llama.cpp 的配置 |
| `partially_load(device, budget)` | 依 GGUF 各 layer 大小算 `n_gpu_layers`；比現況更接近 ComfyUI 的 lowvram 概念 |
| `partially_unload(device, n)` | 先釋放 llama context（KV + compute buffer）並回報釋放量；不夠才走 `detach` |
| `detach` | 釋放 model；權重回到 OS page cache（mmap） |
| `loaded_size` | 以載入前後 `mem_get_info` 的差值實測，不用估算 |
| `_comfy_cache_tensors` | 前綴狀態（`llama_state_seq_get_data`）包成 CPU uint8 tensor 回傳，讓 RAM cache 量得到 |

與現況的差異：mmap 的權重在 OS page cache，不屬於 ComfyUI 的 RAM cache。psutil `available` 把 page cache
算成可用，所以 ComfyUI 不會為它清別的東西；RAM 不夠時由核心自動回收，之後重載才需要讀磁碟（27B ≈ 16.5 GB，
與現況「被 RAM cache 丟掉後重讀 NF4 15–17 GB」相當）。llama.cpp 無法像現況那樣把已在 GPU 的權重搬到 host 再搬回，
只能釋放後重載；page cache 還在時重載主要是 H2D 複製。若有 layer 放在 CPU，那些權重直接從 page cache 讀，
被回收就會 page fault 變慢；這種情況要評估 `use_mlock`。
